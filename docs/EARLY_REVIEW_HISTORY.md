## Pull request 2: Gate: trust only accounts that can write, and re-check after writing

Opened 2026-11-27T13:31:56Z, merged 2026-11-27T13:42:30Z.

Two weaknesses in the first version of the review gate, found by a security check.

**1. A read-only organisation member could record a pass.** A record counted when its comment's `author_association` was `MEMBER`. That is anyone in the organisation, including a member who can only read the repository. The gate now looks up the permission of every account that posts a marker, and counts the record only when the account can write (admin, maintain or write). An `OWNER` is still taken at its word. An account GitHub does not know (404), or a deleted account, is not trusted. Any other failed lookup makes the gate say `error`, so a record the gate could not check is never silently dropped.

**2. A stale pass could overwrite a failure.** Runs for different pull requests are not serialised, and two pull requests can share a head commit. A run that judged the commit before a second pull request was opened on it, or before findings were recorded on a sibling, could write its `success` after another run's `failure`. The gate now judges the commit a second time after it writes the status. If the answer changed it judges and writes again, up to three times, and ends in `error` rather than leave a status it cannot confirm.

What this does not fix: the stale `success` exists for a moment before it is corrected, and a pull request from a fork is still not seen as a sibling of another pull request on the same commit (GitHub's listing omits it). The gate also still does not require the reviewer to be a different account from the author; that is an open question in the factory file spec.

Also in this change: one sentence in the review standard and one open question in the spec.

Once a run has written a status it owns it: a changed answer is written even if the pull request was closed or merged in the meantime (judged on the open pull requests that still share the commit), and a failure to judge again ends in `error`. To support that, a closed pull request is no longer counted among the pull requests judged when open ones share its commit, and `report` is split out of `main`.

Review history: the first review found two blocking problems (a dropped findings record on a failed lookup, and every fork pull request ending in error), fixed in the second commit. The second review found one (a stale `success` left when the pull request is merged before the look back), fixed in the third.

Known and accepted: a record from someone who has since lost write access stops counting, and a record posted by a GitHub App does not count. Both are now stated in the review standard. The permission lookup has not yet run with the real workflow token; the first live run after merge will show it.

Tests: 53 pass locally.

## Independent review: findings

Reviewed by a separate agent that read the whole of `factory/review_gate.py` at this commit and ran the tests (46 pass).

**Blocking**

1. **A failed permission lookup silently drops a `findings` record** (`trust_writers`, the `except Exception` branch). A writer records `pass`; a second writer then records `findings`; the permission lookup for the second writer fails. The findings comment becomes untrusted, the earlier pass stands, and the status is `success`. On main a `MEMBER` was trusted without a lookup, so this is a regression. A failed lookup should make the gate say `error`, like every other failed read.
2. **Every pull request from a fork ends in `error`** (`sharing`, `settled`). The listing of pull requests for a commit does not include a pull request from a fork, so the set read after the write never equals the set judged. The gate writes `success` three times and then `error`, on every run.

**Remarks**

- The race is only partly closed: the re-check compares pull request numbers, so a comment posted on a sibling mid-run is still missed. The description claims more than is fixed.
- The login is not URL-quoted in the permission lookup.
- The `judged is None` branch in `settled` cannot be reached.
- The test helper rewrites `MEMBER` to `COLLABORATOR`, which hides what the Decision tests really use.

**Remarks, to follow up**

1. A stale `success` can survive on the old commit if the head moves between the write and the look back. It needs the original race, two branches at one commit and an unrelated push inside a second or two. The description's "never leave a status it cannot confirm" is slightly too strong.
2. The change to which pull requests are judged when the one asked about is closed is untested and not needed for the fix.
3. Tests that prove less than their names: the merged-before-look-back test closes the pull request one read late; the confirm after a forced write is not pinned; nor are the head commit and description comparisons; the retry inside the API client is untested.
4. The permission lookup has not run with the real workflow token. A 403 would end every reviewed pull request in `error`; a 404 for a real account would silently drop its records. Check both on the first live run.
5. A run killed by the five-minute limit after its first write leaves that status unconfirmed.
6. The description says one sentence was added to the review standard; three were.
